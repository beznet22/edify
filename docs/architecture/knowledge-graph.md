# Knowledge Graph

> The central data structure of the Edify platform. A typed, versioned, queryable graph of ministry knowledge. Every subsystem produces and consumes Knowledge Graph entities.

This spec defines the Knowledge Graph (KG) model: node types, edge types, properties, versioning, query API, embedding strategy, federation rules, and persistence. It is the source of truth for the `schema-kg` SemVer track (per ADR-0014).

---

# Purpose

The KG is the platform's central data structure (per ADR-0005). Three properties make it load-bearing:

- **Knowledge, not documents.** Sermons, lectures, Bible studies, notes, devotionals, and events are nodes in the graph with typed relationships. Documents (recordings, slides, images) are attached as evidence, not primary entities.
- **Queryable relationships.** Cross-feature queries ("every sermon that referenced Romans 8 in the last 5 years") are first-class operations, not N+1 document searches.
- **AI substrate.** Structured knowledge is the substrate that AI agents reason over. The KG enables AI capabilities that would be impossible from raw text.

The KG is local-first (per ADR-0001): every device has its own KG (a subgraph of the user's personal data + workspaces the user is a member of). Sync (per `synchronization.md`) replicates KG mutations across devices.

# Graph model

The KG is a property graph: nodes have typed properties, edges have typed properties, both are versioned.

## Node types (canonical taxonomy)

Every node has a stable type identifier, a stable ID within its type, properties, and provenance.

| Type | Description | MVP scope |
|------|-------------|-----------|
| `Scripture` | A verse, verse range, or chapter within a specific translation | yes |
| `ScripturePassage` | A passage explicitly referenced or quoted in a session | yes |
| `Concept` | An abstract concept (a theological term, a person, a place) | yes |
| `Person` | A named person (biblical figure, historical figure, contemporary individual) | yes |
| `Place` | A geographic location | yes |
| `Sermon` | A preached sermon (single event) | yes |
| `Lecture` | A taught lecture (seminary class, teaching session) | yes |
| `StudySession` | A captured study, sermon attendance, or lecture | yes |
| `Note` | A user-authored note (attached to a StudySession, Scripture, or KG node) | yes |
| `Highlight` | A span of text marked as significant | yes |
| `Bookmark` | A timestamped pointer into a StudySession's timeline | yes |
| `Devotional` | A generated personal reflection | yes |
| `ReadingPlan` | A structured reading schedule | yes |
| `Reading` | An instance of a user completing a reading plan item | yes |
| `Flashcard` | A study flashcard | yes |
| `Quiz` | A quiz instance | yes |
| `Curriculum` | A structured curriculum (collection of StudySessions, ReadingPlans, Quizzes) | yes |
| `Event` | A ministry event (calendar item) | Phase 2+ |
| `Organization` | A church, ministry, or school | yes |
| `Workspace` | A shared ministry workspace within an Organization | yes |
| `Member` | A user identity within a Workspace | yes |
| `Device` | A paired device | yes |
| `Plugin` | An installed plugin | yes |
| `Agent` | A registered AI agent | yes |
| `Asset` | A media asset (recording, slide, image) attached as evidence | yes |

New node types are added via the schema evolution process (per Versioning below). Each new node type must define its properties, edge types it can participate in, and invariants.

## Edge types (canonical taxonomy)

Edges are typed and directional. Edges have properties (confidence, source, timestamp).

| Type | Description | Cardinality |
|------|-------------|-------------|
| `references` | A node explicitly references another (e.g., Sermon references Scripture) | many-to-many |
| `quotes` | A node quotes text from another (e.g., Sermon quotes Scripture verbatim) | many-to-many |
| `derives-from` | A node was derived from another (e.g., Note derives from Scripture) | many-to-many |
| `preached-on` | A Sermon was preached on a date | one-to-many |
| `attended-by` | A StudySession was attended by a Member | many-to-many |
| `authored-by` | A node was authored by a Member | many-to-one |
| `created-by` | A node was generated by an Agent | many-to-one |
| `attaches-to` | An asset is attached to a node | many-to-one |
| `part-of` | A node is part of a larger structure (e.g., Note part of StudySession) | many-to-one |
| `links-to` | A general semantic relationship (with edge properties for specificity) | many-to-many |
| `contradicts` | A node contradicts another (theological, historical, interpretive) | many-to-many |
| `supports` | A node supports the claim or interpretation of another | many-to-many |
| `precedes` | A node precedes another in a sequence | many-to-many |
| `follows` | A node follows another in a sequence | many-to-many |

New edge types are added via schema evolution. Each new edge type must define its source node types, target node types, and properties.

## Property types

Properties on nodes and edges use a constrained type system:

- `string` — bounded length (max 1 MB), Unicode
- `number` — 64-bit float or 64-bit integer
- `boolean`
- `timestamp` — ISO 8601 UTC
- `enum` — one of a fixed set
- `reference` — a typed pointer to another KG node
- `list<T>` — ordered list of T
- `map<string, T>` — keyed map

Properties are versioned. Mutating a property creates a new node version; the old version is preserved (per Versioning below).

# Node identity

Every node has a stable identifier. The identifier scheme depends on the node type:

| Type | Identifier | Example |
|------|-----------|---------|
| `Scripture` | `{translation_id}:{book_id}:{chapter}:{verse_start}:{verse_end}` | `KJV:JHN:3:16:16` |
| `ScripturePassage` | UUID v7 | `0193a8b1-...` |
| `Sermon` | UUID v7 | `0193a8b1-...` |
| `Lecture` | UUID v7 | `0193a8b1-...` |
| `StudySession` | UUID v7 | `0193a8b1-...` |
| `Note` | UUID v7 | `0193a8b1-...` |
| `Person` | UUID v7 | `0193a8b1-...` |
| `Organization` | UUID v7 | `0193a8b1-...` |
| `Workspace` | UUID v7 | `0193a8b1-...` |

UUID v7 is used for generated entities (time-ordered, sortable, low collision risk). Composite identifiers are used for stable entities (Scripture references are identical across translations when normalized, but here we include translation_id to respect theological neutrality).

Stable identifiers enable deterministic sync: the same node on two devices has the same ID, regardless of which device created it first.

# Versioning

Every node and edge is versioned. Mutations do not overwrite — they create a new version.

A node version contains:

- `id` — stable identifier (immutable across versions)
- `version` — monotonic integer starting at 1
- `properties` — the properties at this version
- `created_at` — timestamp
- `created_by` — actor (device, member, agent)
- `supersedes` — pointer to the previous version (null for v1)
- `provenance` — source of the change (user action, agent inference, sync from peer)

Edges are similarly versioned.

## Why versioning

- **Audit trail** — every change is preserved
- **Conflict resolution** — when two devices create conflicting versions, the conflict is detectable and resolvable
- **Undo** — restoring a previous version is a first-class operation
- **Theological neutrality** — preserving old interpretations alongside new ones respects tradition

## Versioning semantics

- A node v2 supersedes v1. Reads return the latest version by default; reads can specify a version or timestamp.
- Deletion is soft: a deleted node has a tombstone version with a `deleted_at` property. Tombstones propagate via sync.
- Edges are versioned alongside their source and target nodes.

## Schema versioning

The KG schema (the set of node types, edge types, property types) is versioned independently of node instances. Schema changes follow the `schema-kg` SemVer track (per ADR-0014).

Breaking schema changes (new required property, removing a node type) bump `schema-kg` major and require migration. Additive changes (new optional property, new node type) bump minor and require no migration.

# Embeddings

Every KG node has zero or more embeddings. Embeddings enable semantic search and similarity queries.

## When embeddings are generated

- **Synchronously (on creation)** — for high-value nodes (Scripture, Concept, Sermon, Note) where semantic search is the primary access pattern
- **Asynchronously (after creation)** — for nodes where embedding can wait (e.g., Highlights)
- **On demand** — for nodes where embedding is rarely needed (e.g., Device, Plugin metadata)

The choice is per node type, declared in the schema.

## Embedding model

- Local: ONNX-hosted sentence-transformers model (per ADR-0010); default `bge-small-en-v1.5` (English) or `bge-small-zh-v1.5` (Chinese); per-locale selection
- Cloud: optional OpenAI `text-embedding-3-small` or similar (per ADR-0010 cloud pluggability); used when local model is unavailable or insufficient

## Embedding storage

Embeddings are stored in a `sqlite-vec` virtual table (per ADR-0008). Each row contains:
- `node_id` — the KG node the embedding represents
- `node_version` — the version of the node the embedding was computed from
- `model_id` — which model produced the embedding
- `embedding` — the vector (typically 384 or 768 dimensions)

When a node is updated, its embedding is recomputed asynchronously. Old embeddings are retained until the new embedding is available, then the old is removed.

## Embedding-based queries

- **Similarity search** — find nodes similar to a query embedding
- **Clustering** — group nodes by embedding proximity
- **Recommendation** — "more like this" across the graph
- **Cross-modal** — embed text and find related images, audio transcripts, etc.

# Query API

The KG query API is a typed Rust API exposed via the engine. Queries are expressed as Rust function calls or as a structured query language (to be designed).

## Query primitives

- **Node by ID** — fetch a node by its stable identifier
- **Nodes by type** — fetch all nodes of a given type (with pagination)
- **Edges from a node** — outgoing edges of given type(s)
- **Edges to a node** — incoming edges of given type(s)
- **Traversal** — walk the graph from a starting node, following typed edges, with depth limit and edge filters
- **Path query** — find paths between two nodes (shortest path, all paths within depth)
- **Vector similarity** — find nodes similar to a query vector
- **Full-text search** — full-text search over node properties (via FTS5)
- **Structured filter** — filter nodes by property values

## Composite queries

Composite queries combine primitives:

- "Every Sermon that referenced Romans 8, with their StudySession attendance, sorted by date"
- "Every Note that derives from a Concept tagged 'eschatology', with the Concept's text and cross-references"
- "Every Member who has attended at least one Sermon preached by Person X"

Composite queries are expressed via a query builder or a structured query language.

## Version-aware queries

Every query can specify:
- `as_of_version` — return the graph state at a specific schema version
- `as_of_timestamp` — return the graph state at a specific time
- Default is "latest"

This enables time-travel debugging and historical analysis.

# Federation rules

The KG on a single device is partitioned:

- **Personal subgraph** — the user's private data (personal Notes, personal Devotionals, personal ReadingPlans)
- **Workspace subgraph(s)** — one subgraph per Workspace the user is a member of (shared Notes, shared StudySessions, shared Events)
- **Organization subgraph** — the Organization's public data (Organization metadata, public Event types, member directory)
- **Shared Scriptural subgraph** — the canonical Scripture data (translations, verses, cross-references) — not user-specific

A user's device KG = personal + workspaces they are members of + organizations they are members of + the shared Scriptural subgraph.

## Tenant isolation

- A node belongs to exactly one partition (personal, workspace, organization, shared)
- Cross-partition queries require explicit authorization
- Sync replicates per-partition (sync within a workspace is independent of sync across workspaces)
- Encryption keys are per-partition (per ADR-0012)

## Privacy

- Personal subgraph is encrypted with a key only the user holds
- Workspace subgraph is encrypted with a key held by the workspace's members
- Organization subgraph is encrypted with a key held by organization members
- Cloud (control plane) never sees subgraph content (per ADR-0001)

# Persistence

The KG is persisted in `kg.db` (per ADR-0008) with the following schema:

- `kg_nodes` — node versions
- `kg_edges` — edge versions
- `kg_node_embeddings` — embeddings (sqlite-vec)
- `kg_node_fts` — full-text index (FTS5)
- `kg_event_log` — KG mutation events (for sync and audit)

SQLite indices:
- `(id, version DESC)` on `kg_nodes` for fast node lookup
- `(source_id, type)` on `kg_edges` for outgoing edge queries
- `(target_id, type)` on `kg_edges` for incoming edge queries
- `(node_id, model_id)` on `kg_node_embeddings` for embedding lookup

Migrations are versioned SQL files (per ADR-0008). Each schema change ships with a migration that runs at engine startup.

# Sync semantics

KG mutations propagate to peers via the sync protocol (per `synchronization.md`). Key semantics:

- **CRDT-based** — node versions and edge versions form a CRDT; concurrent edits are merged deterministically
- **Per-partition sync** — sync is per workspace or per organization; personal subgraph sync is per device
- **Event-tail sync** — KG mutation events are replicated to peers (the same events written to the local event log are sent over the wire)
- **Conflict resolution** — when two devices edit the same node, the CRDT resolves the merge deterministically; manual resolution is required only for non-CRDT cases (rare)

The KG schema is the same on every device. Sync is schema-version-aware: a device with an older schema can sync with a device with a newer schema as long as the nodes and edges the older device sends conform to the older schema.

# Migration

When `schema-kg` bumps a major version:

1. New schema is documented in this spec
2. Migration script is written (versioned SQL file per `kg.db` version)
3. Old data is migrated at engine startup
4. Nodes with data that cannot be migrated are marked with a migration-required flag and rendered read-only
5. Migration is tested across all supported node types and edge types
6. Rollback is supported (the migration is reversible)

Schema migrations are part of the engine's release process and ship in the same release as the schema change.
